## 二、性能指标

本实验选取以下 5 个性能指标：

| 指标 | 含义 | 合理性 |
|---|---|---|
| Prompt 处理速度 | prompt prefill 阶段 tokens/s | 反映模型处理输入上下文的吞吐能力 |
| 生成速度 | autoregressive generation 阶段 tokens/s | 是交互式大模型推理最核心的性能指标 |
| 首 token 延迟 | 从提交 prompt 到首个 token 输出的时间 | 直接影响交互体验 |
| 模型加载时间 | 进程启动到模型可推理的耗时 | 影响服务启动和冷启动性能 |
| 网络延迟/丢包 | RPC 主机和从机之间的 RTT、丢包和重传 | RPC 分布式推理高度依赖网络同步，网络质量会直接影响吞吐 |

其中前三项是官方要求的性能测试核心指标，后两项用于解释 RPC 多机实验中的性能变化。

## 三、单机部署

编译 RPC 版本，同时也可用于普通单机推理：

```bash
cd llama.cpp
cmake -B build-rpc -DGGML_RPC=ON
cmake --build build-rpc --config Release -j 8
```

单机推理命令：

```bash
./llama.cpp/build-rpc/bin/Release/llama-cli.exe \
  -m models/Qwen_Qwen3.5-0.8B-Q4_K_M.gguf \
  -p "Hello, what is AI?" \
  -n 32 \
  --threads 12 \
  --batch-size 512 \
  --no-mmap \
  --ctx-size 2048 \
  --single-turn \
  --perf
```

运行结果正常，输出文件见 `results/single_cli_test.txt`。本次单机测试结果：

```text
Prompt: 131.5 t/s
Generation: 32.8 t/s
```

该命令使用 `--single-turn`，避免推理完成后进入交互模式。

## 四、性能测试

使用 `llama-bench` 测试单机性能：

```bash
./llama.cpp/build-rpc/bin/Release/llama-bench.exe \
  -m models/Qwen_Qwen3.5-0.8B-Q4_K_M.gguf \
  -p 64 -n 64 \
  --threads 12 \
  -mmp 0 \
  -o md
```

结果见 `results/bench_baseline.md`：

| 测试 | 速度 |
|---|---:|
| Prompt 处理 `pp64` | 327.39 ± 21.86 t/s |
| Token 生成 `tg64` | 51.55 ± 7.24 t/s |

`llama-cli` 的端到端输出还包含模型加载、prompt 处理和生成过程，因此生成速度低于纯 `llama-bench` 中的稳定 benchmark 结果。

## 五、参数优化

关键测试结果见 `results/param_key_serial.md`。所有对照均使用同一模型和 `-p 64 -n 64`。

### 5.1 线程数

| threads | pp64 | tg64 |
|---:|---:|---:|
| 4 | 264.99 | 45.39 |
| 12 | 343.46 | 51.22 |
| 16 | 348.36 | 51.94 |

线程数从 4 增加到 12 后，prompt 和生成速度都有明显提升。12 到 16 的收益很小，说明该模型在当前 CPU 上已经接近内存带宽或调度瓶颈。

### 5.2 mmap 开关

| mmap | pp64 | tg64 |
|---|---:|---:|
| 开启 | 303.23 | 49.28 |
| 关闭 `--no-mmap` | 288.19 | 48.72 |

本次短 benchmark 中 mmap 开关差异不大，开启 mmap 略快。考虑到 Windows 环境下文件缓存状态会影响短测结果，最终命令仍保留 `--no-mmap`，用于减少 page fault 抖动并保证模型常驻内存。

### 5.3 batch-size

| batch-size | pp64 | tg64 |
|---:|---:|---:|
| 512 | 265.20 | 47.44 |
| 2048 | 267.14 | 46.96 |

batch-size 对生成阶段影响较小，对 prompt 阶段也只有轻微差别。当前模型较小，内存压力低，因此 batch-size 不是主要瓶颈。

### 5.4 优化结论

本机推荐配置：

```bash
--threads 12 --batch-size 512 --no-mmap --ctx-size 2048 --single-turn
```

主要收益来自线程数调优；batch-size 和 mmap 在当前 0.8B 小模型上影响较小。

## 七、RPC 多机分布式推理

### 7.1 部署方式

从机 Linux 编译：

```bash
cd llama.cpp
cmake -B build-rpc -DGGML_RPC=ON -DGGML_VULKAN=ON
cmake --build build-rpc --config Release -j 32
```

从机 Linux 启动：

```bash
./build-rpc/bin/Release/rpc-server --host 0.0.0.0 -p 50052
```

主机 Windows 运行：

```bash
./llama.cpp/build-rpc/bin/Release/llama-cli.exe \
  -m models/Qwen_Qwen3.5-0.8B-Q4_K_M.gguf \
  -p "Hello, what is AI?" \
  -n 8 \
  --threads 12 \
  --no-mmap \
  --single-turn \
  --perf \
  --rpc 192.168.43.5:50052
```

结果见 `results/rpc_real_cli_n8.txt`：

```text
Prompt: 2.1 t/s
Generation: 1.0 t/s
```

该实验使用 `-n 8`，避免只生成 1 个 token 时出现不稳定的极端 tokens/s 统计。

### 7.2 单机和 RPC 对比

本节同时对应“不同网络环境下 RPC 性能对比”的选做项：localhost RPC 作为低网络开销对照组，真实两机 RPC 使用手机热点网络作为实际无线网络环境。两者性能差异显著，结合 ping 与 Wireshark 结果可判断主要瓶颈来自网络质量。

| 配置 | pp64 / Prompt | tg64 / Generation | 说明 |
|---|---:|---:|---|
| 单机 CPU | 327.39 | 51.55 | `results/bench_baseline.md` |
| localhost RPC | 273.23 | 46.66 | `results/rpc_localhost.md` |
| 真实两机 RPC | 2.1 | 1.0 | `results/rpc_real_cli_n8.txt`，手机热点网络 |

localhost RPC 只比单机略慢，说明 RPC 后端本身可用，构建和调用路径没有明显问题。真实两机 RPC 极慢，主要来自网络。

### 7.3 网络诊断

主机到从机 `ping -n 30 192.168.43.5`，结果见 `results/ping_slave.txt`：

```text
最小 RTT: 9 ms
最大 RTT: 238 ms
平均 RTT: 92 ms
丢包: 0%
```

此前测试中还出现过平均 125 ms、最大 320 ms、3% 丢包。从机抓包观察到大量 TCP 快速重传、乱序接收、超时重传和重复 ACK。两台机器使用手机热点连接。

### 7.4 原因分析

llama.cpp RPC 不是请求级负载均衡，而是张量/计算图级远程后端。主机会把部分模型权重、计算图描述和中间张量通过 TCP 传给从机，每个 token 的计算过程中都可能发生多次同步。手机热点带来高 RTT、抖动、丢包和 TCP 重传，导致每次 RPC 同步等待被放大。

因此，本次真实两机 RPC 性能下降不是程序 bug，而是网络环境不适合细粒度 RPC。若换成有线局域网或稳定 5GHz WiFi，预期性能会明显改善。

## 八、Ray 选择性必做任务

本实验选择 Ray 方向。由于网络环境为手机热点，真实多机服务会受到严重网络抖动影响；因此本部分采用官方允许的资源受限单机模拟方案：在一台主机上启动 `llama-server`，Ray Task 负责分发 25 条 prompt 请求。

### 8.1 Ray 和 llama-server 部署

Ray 版本：

```text
2.55.1
```

启动 llama-server：

```powershell
.\llama.cpp\build-rpc\bin\Release\llama-server.exe `
  -m models\Qwen_Qwen3.5-0.8B-Q4_K_M.gguf `
  --host 127.0.0.1 `
  --port 8080 `
  --threads 12 `
  --no-mmap `
  -np 4 `
  -c 2048
```

Ray 脚本见 `scripts/ray_inference.py`。该脚本记录每个请求的：

```text
start_time
end_time
duration_s
output_length_chars
tokens_generated
tokens_per_second
success
```

prompt 文件为 `prompts.txt`，共 25 条，满足不少于 20 条的要求。

### 8.2 执行方式

运行命令：

```powershell
python .\scripts\ray_inference.py `
  --mode all `
  --n-predict 32 `
  --prompts prompts.txt `
  --output results\ray_results.json
```

结果见 `results/ray_results.json` 和 `results/ray_run.log`。

| 模式 | 请求数 | 成功数 | 总耗时 | 平均延迟 | 最大延迟 | 请求吞吐 | token 吞吐 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 串行 | 25 | 25 | 17.715 s | 0.709 s | 0.870 s | 1.411 req/s | 44.539 tok/s |
| Ray Task 并行 | 25 | 25 | 23.690 s | 5.352 s | 9.474 s | 1.055 req/s | 33.305 tok/s |

### 8.3 Ray 结果分析

Ray 并行模式没有比串行更快，原因是本实验为单机模拟：所有 Ray task 最终请求同一个本地 `llama-server`，而 `llama-server`、Ray worker 和操作系统调度共享同一 CPU 与内存带宽。并行请求增加了 slot 竞争、上下文切换和排队时间，因此平均延迟从 0.709 s 上升到 5.352 s。

这个结果说明 Ray 的价值不在于让单机短任务无条件变快，而在于把大量独立请求调度到多个独立推理服务节点上。在当前资源受限环境下，单机 Ray 模拟完成了任务分发和数据收集，但也暴露了共享资源竞争问题。
